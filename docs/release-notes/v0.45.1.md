## What's new in 0.45.1 — fixes players being unable to connect

**If you are on v0.45.0, update.** A hardening change in that release stopped
players joining your servers ([#150](https://github.com/tubalainen/reforger-server-manager/issues/150)).

## Do I need to do anything?

| If you… | Then |
|---|---|
| Run **v0.45.0** | Update — then **restart each server** so it is rebuilt without the bad setting |
| Run **v0.44.0 or older** | Not affected, but update anyway |

Updating alone is not quite enough for servers that already exist: Docker fixes a
container's security options when it is *created*, so a server built by v0.45.0
keeps the broken setting until it is recreated. The manager now detects that and
rebuilds the container automatically **on the next start** — so stop and start
each server once (or use **Restart**) after updating.

---

## What went wrong

v0.45.0 applied Docker's **`no-new-privileges`** flag to the game server
containers, as part of the security review's container-hardening item.

That flag is inherited by every child process and **cannot be switched off
again** once set. Reforger's **BattlEye** anti-cheat runs as a child of the
server process, so the result was a server that started, looked healthy in the
GUI, and then refused incoming players — reported in game as
`group 1, reason 11`.

It looked like a firewall or port problem, which is the worst part: the ports
were fine the whole time.

## The fix

- Game servers no longer get `no-new-privileges`, restoring exactly the
  behaviour of v0.44.0 and earlier.
- The manager now **notices a container built with the old setting and recreates
  it** on the next start, so the fix reaches servers you already have.
- It remains available as an opt-in for anyone who wants it and has tested it:
  set `INSTANCE_NO_NEW_PRIVILEGES=true` in `.env`.
- The manager's own short-lived helper containers (SteamCMD downloads, cleanup
  jobs) **keep** the flag. They have no anti-cheat, they were working correctly
  in v0.45.0, and they are the ones that run with write access to your data.

## Why it shipped

This was the one change in the security review that could not be verified before
release — it needs a real Docker host running a real Arma server, and the
development environment has no Docker daemon. That limitation was recorded in the
review at the time, but the change was shipped on by default anyway. It should
have been opt-in until proven, which is what it is now.

The security review has been updated with the outcome, so the trade-off is on
record rather than being rediscovered later.

**Upgrading:** as usual — `rsm update`, or refresh the compose file and
`docker compose pull && docker compose up -d`. Then restart each server once.
