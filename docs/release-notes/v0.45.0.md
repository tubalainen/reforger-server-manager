## What's new in 0.45.0 — the rest of the security review

Closes the remaining findings from the
[security review](../security-review-2026-07-27.md) that v0.44.0 left open, plus
a fix to the VPS installer's DNS check.

## Do I need to do anything?

**No.** Nothing here changes how an existing install starts, and no setting is
required. One small behaviour change is worth knowing about:

| If you… | Then |
|---|---|
| Use **engine launch parameters** with `;` `\|` `&` `<` `>` `` ` `` `$` in *Extra args* | The template will refuse to save — see [Breaking changes](#breaking-changes) |
| Everything else | Just [update](#upgrading) |

---

## <a id="breaking-changes"></a>⚠️ Breaking changes

### `extra_args` no longer accepts shell metacharacters

The free-form **Extra args** field on a template's launch parameters now rejects
`;` `|` `&` `<` `>` `` ` `` `$` and newlines. Those characters are how a value
stops being an engine flag and starts being a *shell command*, since the server
image expands `ARMA_PARAMS` through a shell.

Ordinary engine flags (`-myFlag 123`) are unaffected. If a saved template
contains one of these characters, the launch parameters fall back to their
defaults until you edit the field — the server still starts.

## Upgrading

Exactly as in [0.44.0](v0.44.0.md) — no new steps.

```bash
rsm update                      # one-line installs
```

For a by-hand install, refresh the compose file first, then
`docker compose pull && docker compose up -d --remove-orphans`. On Windows, the
Desktop shortcut is enough (nothing in the compose file changed this time).

---

### Containers can no longer gain privileges (R8)

Every container the manager creates — game servers, SteamCMD downloads, the
version check and both cleanup helpers — now runs with **`no-new-privileges`**.
A process inside cannot escalate through a setuid binary, which matters most for
the game servers, since they execute untrusted Workshop mod code as root.

Capability dropping was *not* included: there is no Docker daemon in the
development environment to boot a real Arma server against, and getting it wrong
would show up as servers failing to start. That needs one run on a real host.

### Stored data is no longer world-readable (R5)

`/data` is now `chmod 700`, so the database and every rendered `config.json` —
which hold your server, admin and RCON passwords in clear text — are readable
only by the app user. The **config.json** download button now says plainly that
the file contains those passwords.

Encryption at rest was considered and deliberately skipped: the key would live in
`.env` on the same host as the database it protects, so it guards only against a
leak of the database *alone*, while adding a way to lose every template forever.

### Log out everywhere (R13)

New **`POST /api/auth/logout-all`** rotates the session signing salt, immediately
invalidating every session on every device. Until now, `logout` only cleared your
own cookie — a stolen one stayed valid until it expired, and the only remedy was
changing `SESSION_SECRET` and restarting.

The salt is stored in `DATA_DIR`, so ordinary restarts and updates do **not** log
you out.

### The Workshop dependency walk is bounded (R11)

Resolving a mod's dependency tree now stops at 300 mods or 120 seconds and
reports whatever it could not reach, instead of potentially fetching without
limit. Real mod graphs run to dozens of nodes, so you will not meet either cap.

### Errors no longer leak internals (R14)

Docker and Workshop failures returned the raw exception, which could include host
paths and image internals. They now return a short message and log the detail
server-side. Errors about *your own* config are unchanged — that detail is the
point of them.

### Image pinning: a deliberate non-change (R9)

The review recommended pinning `REFORGER_SERVER_IMAGE` and `STEAMCMD_IMAGE` to
digests. **We decided not to**, because the Arma image has to track game updates
— pinning it would silently leave every install on an old build after a Reforger
release. `.env.example` now explains the trade-off and shows how to pin yourself
if you prefer reproducibility over automatic updates.

### VPS installer: better DNS diagnosis

The pre-flight DNS check compared an IPv4-only lookup against whatever
`getent` returned first, so a dual-stack domain produced a false "does not match"
warning exactly when someone was debugging DNS.

It now checks each record type separately and catches the trap that actually
breaks certificate issuance: **an AAAA record on a server without working IPv6**.
Let's Encrypt *prefers* IPv6 when an AAAA exists, so validation fails however
correct your A record is — the installer now says so explicitly.

### Where the review stands

All 14 findings are now fixed, or accepted with a written rationale. Four
follow-ups remain that need a real host or a change of scope (capability
dropping, rootless Docker, encryption at rest, per-user accounts) — each is
listed under *What remains open* in the review.
