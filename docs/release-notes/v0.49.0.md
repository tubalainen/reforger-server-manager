## What's new in 0.49.0 — the mission header, without the JSON

The **mission header** is how you change a scenario without building one: player
count, XP multiplier, time of day, campaign supply levels, and whatever settings a
mod's own header adds. Until now this manager had no field for it at all — you had
to know the key existed, open **Edit JSON**, and hand-write it into the raw config
([#162](https://github.com/tubalainen/reforger-server-manager/issues/162)).

There is now a **Mission header** section at the bottom of the template's Settings
step.

## Do I need to do anything?

**No.** A template that sets no override renders exactly the `config.json` it
rendered before — the block is written only when it holds something. If you
already hand-wrote a mission header through Edit JSON, it is picked up
automatically and appears in the new section, ready to edit. Nothing changes about
how your server runs.

---

## Settings by name, with the right defaults

Search for a setting and it arrives with the engine's own default already filled
in — `m_fXpMultiplier` at 1, `m_iStartingHours` at 8, `m_eSaveTypes` at 15 — with a
line explaining what it does and which scenarios it applies to. Names, types and
defaults are read off the published mission header classes rather than guessed.

The list is a convenience, never a gate. **Any name you type is written through**,
because which settings a scenario accepts is up to the scenario, and a mod adds its
own. A nested block — ACE's settings tree, for instance — is kept whole and edited
as JSON instead of being flattened into rows that misrepresent its shape.

Where one setting depends on another, the section says so: adding `m_iStartingHours`
points out that `m_bOverrideScenarioTimeAndWeather` has to be on first, and offers
to switch it on.

## Paste it from wherever you got it

Almost nobody writes a mission header from scratch — it comes from a forum post, a
Discord message, someone else's `config.json`, or another control panel's box. So
there's a **Paste from AMP or a config…** button that accepts all of it:

- AMP's brace-less format, `"m_iPlayerCount":"64","m_eEditableGameFlags":"6"`
- a whole `config.json`, or just the `"missionHeader": { … }` part
- a snippet with ragged indentation, mixed tabs, comments, trailing commas, curly
  quotes from a web page, unquoted setting names, or missing commas between lines
- a copy that got **cut off mid-block**, with its closing braces missing — the usual
  result of dragging a selection out of a scrolled text box

It repairs what it can, then tells you exactly what it changed ("closed 2 unclosed
braces", "removed comments"), shows how many settings would be added, changed or
left alone, and inserts nothing until you press Insert. Indentation is never your
problem: the text is parsed into settings and re-rendered, so what lands in
`config.json` is correctly formatted by construction.

Two things it will not do:

- **It never reinterprets a value.** AMP writes numbers quoted (`"64"`), the
  documented examples write them bare (`64`), and nothing states whether the engine
  accepts both. So yours is left exactly as you pasted it, with a one-click
  conversion offered if you want it.
- **It never guesses a deletion.** Missing closing braces are added; a *surplus*
  one means the paste was misread, and it stops and says so rather than quietly
  dropping half your settings.

## Everything else keeps working

- Every override lands in the template's change log by name, e.g.
  `game.gameProperties.missionHeader.m_fXpMultiplier: 1 → 10`.
- Mission header keys no longer count towards the "custom keys" badge. The wizard
  manages the whole block now, so its contents are not hand-edits to preserve.
- Editing the header in the raw **Edit JSON** panel still works and flows into the
  new section, rather than coming back as an unmanaged custom key.

## A note on what we could not verify

`m_eSaveTypes` and the two `…GameFlags` settings are bit masks whose individual bit
values are not published anywhere we could confirm. Rather than ship a
tick-box helper built on a guess, they are plain number fields carrying the
documented default. Similarly, some settings are reported by players as being
ignored by certain stock scenarios — where that is known, the section says so
instead of promising a result.
