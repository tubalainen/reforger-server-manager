## What's new in 0.44.0 — security hardening

This release is the result of a full security review of the project
([`docs/security-review-2026-07-27.md`](../security-review-2026-07-27.md)), which
ranked every finding for a deployment exposed to the internet. Six findings are
addressed here, plus one-line Linux installers and a hardened VPS deployment.

**Nothing changes for an existing localhost install** beyond the new socket
proxy container: the default `127.0.0.1` bind stays as relaxed as before.

### The Docker socket is no longer mounted into the manager (R1)
Talking to the Docker daemon is root-equivalent on the host. The manager now
reaches it through a bundled least-privilege **`docker-socket-proxy`** that
forwards only what the manager uses (containers, images, networks, info) and
denies the rest — `exec`, `build`, volume create, swarm, secrets and more. The
proxy sits alone on an `internal` network, so it is unreachable from the game
server containers, which run untrusted Workshop mods as root.

### The app refuses to start in an unsafe exposed configuration (R2, R3)
When the GUI is bound to anything other than a loopback address, the manager now
**refuses to start** if `ADMIN_PASSWORD` is still the example value or empty, or
if `AUTH_ENABLED=false` without the new `AUTH_DELEGATED_ACK=true`.

Letting a reverse proxy own authentication is still fully supported — that is
exactly what `AUTH_DELEGATED_ACK=true` acknowledges. A localhost bind is
unaffected and still starts with warnings only.

The session cookie is now marked `Secure` automatically when the request arrives
over HTTPS (including via a proxy's `X-Forwarded-Proto`), with no configuration.

### Login throttling now identifies the real client (R4)
Behind a reverse proxy every request appears to come from the proxy, so the
per-IP login limit had collapsed into a single shared bucket: attackers were not
slowed individually, and one of them could exhaust it and **lock every operator
out**. The manager now resolves the real client from `X-Forwarded-For`, but only
when the direct peer is listed in the new `TRUSTED_PROXIES` setting, so the
header cannot be forged.

Throttling is per client with an escalating lockout (60s → 5m → 15m → 1h), a
successful login clears it, and failed logins are now logged.

### API docs closed, build details behind auth (R6)
`/docs`, `/redoc` and `/openapi.json` are disabled unless `API_DOCS=true` is set
for development. `/api/health` reports liveness only, and the precise version
now requires a session.

### Security headers and CSRF protection (R7, R12)
Every response carries a strict `Content-Security-Policy` (no third-party
sources, no inline script), `X-Frame-Options: DENY`, `nosniff`,
`Referrer-Policy: no-referrer`, and HSTS when served over HTTPS. State-changing
requests are rejected when a browser reports a foreign `Origin`, and all three
WebSocket handshakes now validate `Origin` before accepting the connection.

### One-line installers for Linux
Linux gets the same treatment Windows already had:

```bash
# Local box (home / LAN)
curl -fsSL https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/scripts/linux/install-local.sh | sudo sh

# Public VPS — adds automatic HTTPS via Caddy
curl -fsSL https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/scripts/linux/install-vps.sh | sudo sh
```

They check for Docker (offering to install it), generate a strong password and
session secret, set up the firewall after confirming with you — always allowing
your **current SSH port first**, so a remote session cannot be cut off — and
install an `rsm` command for `start`/`stop`/`status`/`logs`/`update`/`config`/
`uninstall`.

### New: hardened VPS deployment
`docker-compose.vps.yaml` runs **Caddy** in front with automatic Let's Encrypt
certificates. The manager publishes no port of its own and is reachable only
through Caddy; the Docker API sits behind the socket proxy on an internal
network. Set `SITE_ADDRESS` to your domain and it just works.

### Documentation fixes
- The local Linux instructions now give the actual `ufw` commands, instead of
  only mentioning "any firewall on the host".
- The VPS instructions now cover the **provider-level firewall** (Hetzner, AWS,
  Oracle, GCP, DigitalOcean), which sits in front of `ufw` and blocks almost
  everything by default — the most common reason a server is unreachable.

### New settings
`AUTH_DELEGATED_ACK`, `TRUSTED_PROXIES`, `API_DOCS`, `ALLOWED_ORIGINS`,
`CONTENT_SECURITY_POLICY`, `SITE_ADDRESS` and `PROXY_SUBNET` (VPS only). All are
documented in `.env.example`; every one has a safe default, so an existing
`.env` keeps working unchanged.

### Still open
`R5`, `R8`, `R9`, `R10`, `R11`, `R13` and `R14` from the review are not in this
release — see the report for the ranked backlog.

**Upgrade:** the manager updates itself on start, or pull
`ghcr.io/tubalainen/reforger-server-manager:latest`. Because the Docker socket
mount moved into a new service, run `docker compose up -d` (not just `restart`)
so the new `docker-socket-proxy` container is created.
