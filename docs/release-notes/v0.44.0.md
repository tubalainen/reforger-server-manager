## What's new in 0.44.0 — security hardening

This release is the result of a full security review of the project
([`docs/security-review-2026-07-27.md`](../security-review-2026-07-27.md)), which
ranked every finding for a deployment exposed to the internet. Six findings are
addressed here, plus one-line Linux installers and a hardened VPS deployment.

**A default localhost install keeps working untouched** — the `127.0.0.1` bind
stays as relaxed as before. If you changed `WEB_BIND`, disabled the login, or
script anything against the API, read **Breaking changes** below first.

---

## ⚠️ Breaking changes

### 1. An exposed install with a weak or missing password now refuses to start
If `WEB_BIND` is anything other than a loopback address, the manager **will not
start** when:

- `ADMIN_PASSWORD` is still `change-me-now`, or is empty; or
- `AUTH_ENABLED=false` and `AUTH_DELEGATED_ACK` is not set to `true`.

This is the intended protection — an internet-reachable GUI that controls Docker
should never run on the example password — but it *will* stop a server that
previously started. The container log prints a `SECURITY:` line naming exactly
what to fix.

**To fix, pick one:** set a strong `ADMIN_PASSWORD`; or set
`AUTH_DELEGATED_ACK=true` if a reverse proxy in front already authenticates every
request; or set `WEB_BIND=127.0.0.1`.

> A `$` in the password must be written twice (`$$`) in `.env` — Docker Compose
> eats a single one and the value arrives empty, which now blocks startup rather
> than silently breaking the login.

### 2. `/api/health` no longer reports the version
It returns `{"status": "ok"}` only. **Any uptime check or monitor that parses
`version` from `/api/health` will break.** Check the `status` field instead.

### 3. `/api/version` returns less to anonymous callers
Without a session it returns only `name` and `auth_enabled`; `version` and
`repo_url` now require a login. Scripts that read the version anonymously need to
authenticate first.

### 4. The interactive API docs are gone by default
`/docs`, `/redoc` and `/openapi.json` return **404**. If you generate a client
from the OpenAPI schema or use the Swagger UI, set `API_DOCS=true` in `.env`.

### 5. Cross-origin browser requests are rejected
A state-changing request whose browser `Origin` does not match the `Host` is
refused with **403**. Command-line clients (`curl`, scripts) send no `Origin` and
are unaffected. If a browser-based tool on another origin drives the API, list it
in `ALLOWED_ORIGINS`.

### 6. The compose file changed — pulling the image alone is not enough
A new `docker-socket-proxy` service and an `internal` network were added. **The
new image works fine with an old compose file** (it falls back to the mounted
socket), so nothing breaks if you skip this — but you will not get the R1 socket
hardening until you update the compose file itself. See **Upgrading** below.

### 7. Behind a reverse proxy, set `TRUSTED_PROXIES`
Not a breakage, but required to actually benefit from the login-throttling fix.
Until it is set, every request still looks like it comes from the proxy, so
throttling stays one shared bucket. `docker-compose.vps.yaml` sets it for you.

## Upgrading

### Linux — installed with the one-line installer
```bash
rsm update
```
The installers are new in this release, so anything installed with them already
has the socket proxy. Note that `rsm update` pulls images and restarts — it does
not re-download the compose file, so if a future release changes that file,
re-run the installer (it keeps your `.env`).

### Linux — installed by hand
**Refresh the compose file first.** The compose file lives in your folder, not in
the image, so pulling alone cannot deliver the new `docker-socket-proxy` service —
and `restart` will not create it either:
```bash
cd /path/to/your/install

# 1. refresh the compose file (docker-compose.vps.yaml if that's what you run)
curl -fsSLO https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/docker-compose.yaml

# 2. pull and apply
docker compose pull
docker compose up -d --remove-orphans
```
Your `.env` is untouched; every new setting has a safe default. Compare it
against the latest [`.env.example`](https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/.env.example)
if you want the new options documented locally.

`--remove-orphans` is optional and cannot touch your game servers — those are
sibling containers created through the Docker API, carrying no Compose project
labels, so Compose cannot see them.

### Windows
Double-clicking the Desktop shortcut updates the PowerShell scripts and pulls the
new image, so **all the application-level fixes above apply immediately** — but
it deliberately leaves your `docker-compose.windows.yaml` alone, so the socket
proxy is *not* added.

To get that too, re-run the installer (it keeps your existing `.env`, including
your password):
```powershell
$installer = "$env:TEMP\rsm-install.ps1"
Invoke-WebRequest -UseBasicParsing https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/scripts/windows/install.ps1 -OutFile $installer
powershell -ExecutionPolicy Bypass -File $installer
```

Then start it from the shortcut as usual. Nothing else about the Windows setup
changes: the same image, the same data, the same firewall rule, and the
start/stop/uninstall scripts handle the extra container on their own.

### Expect a short server outage
Replacing the manager container stops every running game server on the way down;
the instances with **auto-start** enabled come back on their own once it is up
again. Upgrade at a quiet moment if players are online.

### Any setup, verifying it worked
`docker ps` should list a `reforger-docker-proxy` container alongside
`reforger-manager`. If it does not, the compose file was not updated — the image
is new but the stack is still wired the old way.

### Rolling back
Pin the previous version and bring the stack up again:
```
MANAGER_VERSION=v0.43.8
```
Nothing in this release changes the database schema or the on-disk layout, so a
downgrade is safe, and the older image works with either compose file (it reads
`DOCKER_HOST` the same way).

---

### The Docker socket is no longer mounted into the manager (R1)
Talking to the Docker daemon is root-equivalent on the host. The manager now
reaches it through a bundled least-privilege **`docker-socket-proxy`** that
forwards only what the manager uses (containers, images, networks, info) and
denies the rest — `exec`, `build`, volume create, swarm, secrets and more. The
proxy sits alone on an `internal` network, so it is unreachable from the game
server containers, which run untrusted Workshop mods as root.

### The app refuses to start in an unsafe exposed configuration (R2, R3)
When the GUI is bound to anything other than a loopback address, the manager now
**refuses to start** if `ADMIN_PASSWORD` is still the example value or empty, or
if `AUTH_ENABLED=false` without the new `AUTH_DELEGATED_ACK=true`.

Letting a reverse proxy own authentication is still fully supported — that is
exactly what `AUTH_DELEGATED_ACK=true` acknowledges. A localhost bind is
unaffected and still starts with warnings only.

The session cookie is now marked `Secure` automatically when the request arrives
over HTTPS (including via a proxy's `X-Forwarded-Proto`), with no configuration.

### Login throttling now identifies the real client (R4)
Behind a reverse proxy every request appears to come from the proxy, so the
per-IP login limit had collapsed into a single shared bucket: attackers were not
slowed individually, and one of them could exhaust it and **lock every operator
out**. The manager now resolves the real client from `X-Forwarded-For`, but only
when the direct peer is listed in the new `TRUSTED_PROXIES` setting, so the
header cannot be forged.

Throttling is per client with an escalating lockout (60s → 5m → 15m → 1h), a
successful login clears it, and failed logins are now logged.

### API docs closed, build details behind auth (R6)
`/docs`, `/redoc` and `/openapi.json` are disabled unless `API_DOCS=true` is set
for development. `/api/health` reports liveness only, and the precise version
now requires a session.

### Security headers and CSRF protection (R7, R12)
Every response carries a strict `Content-Security-Policy` (no third-party
sources, no inline script), `X-Frame-Options: DENY`, `nosniff`,
`Referrer-Policy: no-referrer`, and HSTS when served over HTTPS. State-changing
requests are rejected when a browser reports a foreign `Origin`, and all three
WebSocket handshakes now validate `Origin` before accepting the connection.

### One-line installers for Linux
Linux gets the same treatment Windows already had:

```bash
# Local box (home / LAN)
curl -fsSL https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/scripts/linux/install-local.sh | sudo sh

# Public VPS — adds automatic HTTPS via Caddy
curl -fsSL https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/scripts/linux/install-vps.sh | sudo sh
```

They check for Docker (offering to install it), generate a strong password and
session secret, set up the firewall after confirming with you — always allowing
your **current SSH port first**, so a remote session cannot be cut off — and
install an `rsm` command for `start`/`stop`/`status`/`logs`/`update`/`config`/
`uninstall`.

### New: hardened VPS deployment
`docker-compose.vps.yaml` runs **Caddy** in front with automatic Let's Encrypt
certificates. The manager publishes no port of its own and is reachable only
through Caddy; the Docker API sits behind the socket proxy on an internal
network. Set `SITE_ADDRESS` to your domain and it just works.

### Documentation fixes
- The local Linux instructions now give the actual `ufw` commands, instead of
  only mentioning "any firewall on the host".
- The VPS instructions now cover the **provider-level firewall** (Hetzner, AWS,
  Oracle, GCP, DigitalOcean), which sits in front of `ufw` and blocks almost
  everything by default — the most common reason a server is unreachable.

### New settings
`AUTH_DELEGATED_ACK`, `TRUSTED_PROXIES`, `API_DOCS`, `ALLOWED_ORIGINS`,
`CONTENT_SECURITY_POLICY`, `SITE_ADDRESS` and `PROXY_SUBNET` (VPS only). All are
documented in `.env.example`; every one has a safe default, so an existing
`.env` keeps working unchanged.

### Still open
`R5`, `R8`, `R9`, `R10`, `R11`, `R13` and `R14` from the review are not in this
release — see the report for the ranked backlog.

**Upgrading:** see [Upgrading](#upgrading) above — this release needs more than an
image pull, and one configuration case will refuse to start until you fix it.
