## What's new in 0.54.1 — Backups that know which server they belong to

0.54.0 gave every instance a shelf of saved worlds. A server changes template
over its life, so that shelf fills up with worlds from setups the server no
longer runs — and the card would tell you a backup came from somewhere else and
then leave you there. This release makes the shelf usable across templates
([#181](https://github.com/tubalainen/reforger-server-manager/issues/181)).

## Do I need to do anything?

**No.** No `.env` or compose change, and existing backups gain all of this: the
matching is worked out from what each archive already recorded.

## Every backup says whether this server can read it

A world is loaded by the scenario that wrote it, out of the hive id its template
names. Those two facts — not the template's name — decide whether a restore is
visible in game, so each row is now badged against what the instance is set to
right now:

- **matches this server** — restore it and the world is there.
- **different scenario** — a scenario does not read another scenario's world.
- **different save (hive id)** — the case that used to pass silently. Two
  templates on the same scenario with different hive ids load different worlds;
  the files look right, the server starts empty, and nothing said why.
- **origin unknown** — an uploaded archive that never recorded what wrote it.

The card also prints what the server is set to, so the badges have something
visible to be measured against.

## …and which template does read it

When a backup does not match, the manager looks for a template on this manager
that writes to that save — preferring the one recorded on the backup, falling
back to any template with the same scenario — and the row says **loads under
template "X"**.

The restore dialog turns that into one action: **Switch template & restore**
repoints the instance and puts the world back, ticked by default. The template is
switched first, so a failure there leaves the instance untouched rather than
holding a world it cannot read.

If nothing on this manager targets that save, the dialog says so plainly instead
of offering a swap that would not help — restore the files anyway if you want
them in place, then build a template with that scenario.

The template that wrote a backup can be renamed, edited or deleted; matching is
done on the scenario and hive id it recorded, so a renamed template still matches
and a deleted one simply drops out of the offer.

## A restore now has an undo

Restoring deletes the world it replaces — that is what makes it a restore rather
than a merge — and it was the one destructive action here without a safety net,
while the far milder template swap had one. The confirmation now offers **Back up
the world being replaced first**, ticked by default; it lands on the shelf as
*Replaced by a restore*.

That copy cannot cost you the archive you are restoring: the shelf is capped at
ten, and the oldest backup — the one a new arrival would push off — may be
exactly the one being unpacked. Pruning now protects it.

## Small print

- Backups belong to the instance, not to a template. Swapping a template never
  moves, copies or deletes one; it only changes which of them the server can read.
- A backup is labelled with the template the instance was on when it was taken,
  which is why the automatic backup before a template change is taken *before*
  the swap.
- The instance header refreshes as soon as a restore repoints it, rather than
  showing the old template until the next poll.
