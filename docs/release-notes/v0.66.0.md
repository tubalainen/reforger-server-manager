## What's new in 0.66.0: several teams on one machine, and passwords the team can change

v0.65.0 made it safe for several installs to share a machine. This release
makes it practical: whoever manages the machine adds a team's install with one
command, and each team runs theirs from its own web GUI, password included.

- **Change the login password in the GUI.** Under the new **System › Account**
  page. It needs the current password and at least 12 characters, and it takes
  effect at once. Everyone else signed in with the old password is logged out;
  you stay signed in. The password is stored hashed in the install's own
  database, and the `ADMIN_PASSWORD` in `.env` stops working from then on.
  **Log out everywhere** on the same page ends every session, yours included.
- **A forgotten password is reset by whoever manages the machine**, with
  `sudo rsm reset-password`. The `.env` password then works again, and
  everyone is logged out.
- **A second team's install in one command** (#204). On Linux,
  `sudo rsm add-stack team2` sets up a complete install next to the first. It
  gets its own folder, the next free GUI port and UDP port ranges, a generated
  password, firewall rules, and starts it. On Windows, the installer takes
  `-Stack team2` for the same. See
  [Several installs on one machine](https://github.com/tubalainen/reforger-server-manager/blob/main/docs/installation.md#several-installs-on-one-machine).
- **`rsm` knows every stack on the machine:** `rsm stacks`, `rsm ports` (which
  also flags overlapping ports), `rsm remove-stack`, and `--stack NAME` on
  every command. `start`, `stop`, `restart`, `status`, `update` and `check`
  also take `--all`. With more than one stack, a command must say which stack
  it is for, so `rsm` never stops the wrong team's servers on a guess.
- **Every server's ports stay inside its manager's ranges.** A port outside
  them is now refused, because on a shared machine it may be another team's.
  A port set before this release keeps working. **System › Ports & firewall**
  lists any such server, so you can move it into range.

## Do I need to do anything?

**No.** Nothing changes until you use the new features. A single install stays
exactly as it is.

## Updating your setup files

Only the `rsm` command changed. The compose files and `.env` did not.

- **Linux with the installer (`rsm`):** run `sudo rsm update` as usual. At the
  end it updates the `rsm` command itself; the new commands work from the next
  run. The first time the new `rsm` runs as root, it moves
  `/etc/reforger-server-manager.conf` to
  `/etc/reforger-server-manager/stacks/reforger.conf`. That happens by itself.
  If you pin `MANAGER_VERSION`, the `rsm` you run updates itself from the
  pinned release, so the new commands arrive once you pin `v0.66.0` or later.
- **Linux, installed by hand:** nothing to do. To let `rsm` drive an install,
  see the end of *By hand* in the installation guide.
- **Windows:** nothing to do. The scripts update themselves the next time you
  start the manager from its shortcut.

## Small print

- The startup safety check now judges the password actually in effect. With a
  password set in the GUI, the example or a short `ADMIN_PASSWORD` in `.env`
  no longer counts against a network-exposed install.
- `rsm add-stack` refuses to run while any install on the machine still lacks
  the Docker gate (a compose file older than v0.65.0). Such a manager would
  treat the new stack's servers as its own.
- On a VPS set up with Caddy, a second stack has no HTTPS front of its own yet.
  `rsm add-stack` keeps its GUI on the machine (an SSH tunnel) and says so. A
  shared front for several teams is the next phase of #204.
- Windows: a second install gets its own firewall rule and Desktop shortcut,
  named after the stack. `uninstall.ps1` removes the install it sits in, and it
  keeps the Docker images while other installs still use them.
- The Linux installers register their install for `rsm`. Run a second time
  against a different folder, they point you at `rsm add-stack` instead of
  installing a second copy.
- A new CI job runs the real installer and `rsm` on a Linux machine. It adds a
  second stack, lists it, checks its ports and removes it again.
