## What's new in 0.67.0: the Server Supervisor, every team's servers on one page

A machine can run several teams' installs since v0.65.0. This release gives
whoever manages that machine one page that shows all of them: the **Server
Supervisor** ([#204](https://github.com/tubalainen/reforger-server-manager/issues/204)).
It is read-only. Each team still runs its servers from its own manager.

- **Every stack at a glance.** For each team's install: whether its manager and
  Docker gate are running, the manager's version, the ports it takes, and each
  game server with its status, players and player limit, FPS, CPU, memory and
  uptime. Above them the totals for the whole machine, each with the last hour
  as a small graph.
- **Needs attention.** One list of what the host administrator should look at:
  a manager or gate that is down, a stack still without a Docker gate, two
  stacks whose ports overlap, a port two servers share, a server outside its
  stack's port range, a server that keeps restarting or ran out of memory, a
  Docker Engine too old for game servers, a machine whose CPU or memory is
  nearly full, and managers older than the Supervisor.
- **It cannot change anything, and it never sees a team's secrets.** It is its
  own install with its own login, on port 7090, bound to `127.0.0.1` by
  default. Only its *observer* container can reach Docker. The observer has no
  network and is not a Docker proxy: it passes on each container's name, state
  and ports, and a game server's player count and FPS, never an environment
  (where a team's password is), a command line or the text of a log.
- **Set it up with one command.** On Linux: `sudo rsm supervisor install`
  (plus `status`, `logs`, `update`, `stop`, `start`, `restart` and `remove`).
  `sudo rsm update --all` updates it together with every stack. On Windows:
  the installer with `-Supervisor`, which adds a **Reforger Server Supervisor**
  shortcut to the Desktop. See
  [The Server Supervisor](https://github.com/tubalainen/reforger-server-manager/blob/main/docs/installation.md#the-server-supervisor).
- **Fixed: signing in to one team's GUI signed you out of another's** on the
  same machine. A browser keeps one set of cookies per host name, whatever the
  port, and every install used the same cookie name. Each stack now has a
  cookie of its own. The first install keeps its old one, so nobody is signed
  out by the update.

## Do I need to do anything?

**No,** unless you want the Supervisor. A single install keeps working as it
is. Each game server is recreated once, the next time it starts, to carry its
name, player limit and ports for the Supervisor. Its data is untouched.

## Updating your setup files

The compose files changed a little: each stack's Docker gate now carries a
label, so the Supervisor can recognise it. Nothing breaks without them — the
Supervisor finds an unlabelled gate by its name — but take the new file when it
is offered. The Supervisor has a new compose file of its own,
`docker-compose.supervisor.yaml`, and its own `.env.supervisor.example`; the
Supervisor's install commands download both. `.env` did not change.

- **Linux with the installer (`rsm`):** run `sudo rsm update` (or
  `sudo rsm update --all` with several stacks). Say yes to the new compose file
  and to recreating the stack. Game servers stop briefly; auto-start ones come
  back by themselves. At the end `rsm` updates itself, and
  `sudo rsm supervisor install` works from the next run.
- **Linux VPS:** the same, with `sudo rsm update`.
- **Linux, installed by hand:** download the compose file you use again
  (`docker-compose.yaml` or `docker-compose.vps.yaml`), then
  `docker compose pull`, `docker compose down` and `docker compose up -d`.
- **Windows:** re-run the installer (with `-Stack NAME` for a second stack) to
  get the new `docker-compose.windows.yaml`; your `.env` is kept. Or leave the
  old file: everything works without the label. `install.ps1 -Supervisor`
  installs the Supervisor.

## Small print

- A stack is found from the labels its compose file gives its manager, which
  stacks have had since v0.65.0. Older installs do not show up; update them.
  A manager older than v0.67.0 shows no version, and its servers are listed as
  *Server 1*, *Server 2* and so on until they are next started.
- A server that has no container is not listed: one that was never started, or
  one whose manager removed it on the way down.
- The Supervisor's password is `ADMIN_PASSWORD` in its own `.env`. Changing it
  on the page is not possible; change the file and restart it.
- A stack's Docker gate now refuses to create a container that claims to be a
  manager or a gate, so a team's manager cannot plant a fake one in the
  Supervisor's view.
- The image carries its version as a label (`reforger-manager.version`), which
  is how the Supervisor reads each manager's version. CI keeps it equal to the
  app's version.
- A new CI step brings the Supervisor up next to two stacks on a real Docker
  host, checks it sees both with their servers and players and none of their
  passwords, then stops one stack's manager: the Supervisor flags it, and the
  other stack's server keeps running. Another runs `rsm supervisor install` and
  `remove` next to the installer's stacks.
- Not yet tested on a real Windows PC or with real Arma servers: the Windows
  `-Supervisor` option, and the figures of a real server under load. Please
  report anything that looks off.
