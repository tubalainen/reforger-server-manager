## What's new in 0.55.0 — Restore it anyway

The manager knows when a saved world will not load: a world is read by the
scenario that wrote it, out of the hive id its template names, and 0.54.1 taught
every backup to say whether it matches. That rule is right almost always. The
rest of the time you are right — a scenario id that changed upstream, a mod that
moved its data, a world you are deliberately transplanting onto a new template —
and the manager had no way to get out of your way
([#184](https://github.com/tubalainen/reforger-server-manager/issues/184)).

Now it does, behind a warning and a tick.

## Do I need to do anything?

**No.** No `.env` or compose change. Restores that already fitted behave exactly
as before; nothing about your existing backups changes.

## Pick the template a world is restored under

The restore dialog gains a template picker. Every template you have is listed,
each labelled with how it fits *this* backup:

> Antons Testserver Karlslo — different scenario (current)
> Freedom Fighters — matches this backup

It starts on the template that reads the world, so the ordinary case is still one
click. Choose a different one and the instance is repointed as part of the
restore, exactly as before — you are simply no longer limited to the manager's
recommendation.

## Force

Pick a template that does not fit and the dialog turns red, says precisely why —

> This world was written under scenario `{ABCDEF…}Missions/FreedomFighters.conf`,
> and template "Antons Testserver Karlslo" runs
> `{DAA03C6E…}Missions/24_CombatOps.conf`. A scenario does not read another
> scenario's world.

— and the button becomes **Force restore**, disabled until you tick *I know why
this combination is right*.

Two things are not negotiable on that path:

- **The world being replaced is always backed up first.** The checkbox is ticked
  and locked. A forced restore is the one most likely to be wrong, so its undo is
  not optional — and that safety copy can never prune the archive being restored.
- **It is written to the manager log**, with the backup, the template and the
  reason it did not fit.

Afterwards, start the server and check the world actually loaded. The manager can
put the files in place; only the game can tell you it read them.

## The rule is now actually enforced

Worth knowing if you drive the API directly: until this release the fit rules were
advice the GUI drew, and `POST /api/instances/{id}/backups/{id}/restore` would
unpack anything at all. It now refuses a restore whose result would not load —
wrong scenario, wrong hive id, or an archive that never recorded either — with
`409` and the reason. `{"force": true}` is the one way past it, and it turns the
safety copy on regardless of what else the request said.

An archive with no recorded origin — a hand-rolled tarball rather than one this
manager wrote — counts as "cannot be checked" and needs the same tick. The manager
will not claim a world is safe to restore when it has no way to know.

## Small print

- Choosing the template the instance already runs no longer tears its container
  down for nothing.
- The dialog's explanation now describes the template you picked, not whichever
  one the instance happened to be on when you opened it.
