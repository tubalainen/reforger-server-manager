## What's new in 0.54.0 — Your world, in a file you can keep

Changing a server's template or its scenario replaces what the server writes to
disk. The world your players built stays on the host, but the new setup does not
read it, and until now the only way to keep a copy was to know where the files
were and copy them by hand over SSH — while hoping you copied the right ones.

This release gives every instance a **Saved game backups** card
([#179](https://github.com/tubalainen/reforger-server-manager/issues/179)): one
archive of that server's world, made in a click, restorable in a click,
downloadable to keep off the box — and offered to you automatically the moment
you swap the instance to another template.

## Do I need to do anything?

**No.** No `.env`, compose or configuration change. Existing servers keep
running exactly as they were, and the new card is empty until you use it.

## A backup holds more than `.save`

The manager used to treat the persistent save — `.save/`, and files ending
`.db` — as the whole of a server's saved state. On a plain Game Master server
that is true. On anything running scenario mods it is badly wrong.

A Freedom Fighters profile looks like this:

```
profile/profile/
  .save/            the world
  .db/              a mod database
  CRX_EAI/          mod state
  DarcMods/         mod state
  FFLootTransfer/   what your players stashed
  FFShopOverhaul/   the shops
  FFShopPricing/    what things cost
  FreedomFighters_ServerConfig.json
  ownerToken.bin    (the server's identity, not world state)
```

Everything above except the last line is state that scenario built up, and none
of it was being counted or offered for backup. So the rule is now the other way
round: **everything in the profile is saved game data except what provably is
not** — the logs, the downloaded mod bake, and `ownerToken.bin`.

That fixes the readout too. The **Stored data** card's save row is now called
*Saved game data*, lists the paths it actually found, and reports the real size —
where it used to say "3 KB" for a server with a busy economy. It is the same
definition a backup uses, so what the card offers to delete and what a backup
holds can never drift apart.

## Making one

**Back up now** writes a `.tar.gz` under
`./data/instances/<id>/backups` on the host, with an optional label. It works
while the server is running — a backup is only a read — and the row says so when
one was taken from a live server, because a save point being written at that
exact moment can land in the archive half-finished. Stop the server first if the
copy has to be perfect.

Each backup remembers which instance, template and scenario wrote it, and carries
that inside the archive as well as beside it — so a file you downloaded a year
ago can still tell you what it is.

## Putting one back

**Restore** needs the server stopped. It deletes the current saved game data and
unpacks the backup in its place — not a merge: a world half from one save and
half from another is not a restore. Logs, the mod bake and the server's identity
token are left alone.

If the backup was written under a different scenario than the one the instance is
now set to, the row and the confirmation both say so. The manager does not stop
you — the files are real, and you may know exactly what you are doing — but a
world from another scenario usually will not load.

## Before a template change, automatically

The **Change template** form now offers *Back up the saved game data first*,
ticked by default whenever there is anything to lose, with the size next to it.
The backup is taken **before** the instance is repointed, so it is labelled with
the template that actually wrote it — and it lands on the shelf as *Made before a
template change*.

## Off the box, and back on

**Download** hands you the archive, named for the instance and the moment it was
taken. **Upload a backup file** puts one back on the shelf: on a rebuilt host, on
a fresh install, or onto a different instance.

An uploaded archive is the only file here the manager did not write, and it is
unpacked as root, so it is checked as a whole before it is accepted: only plain
files and directories, only below `profile/`, no symlinks, no absolute paths, no
`..`, and a ceiling on what it unpacks to. Anything else is refused rather than
cleaned up.

## Small print

- The newest **ten** backups are kept per instance; older ones are removed as new
  ones are made.
- Backups live with the instance, so deleting an instance *and its data* deletes
  its backups too. Download the ones that matter.
- Making a backup does not need Docker — it is a plain read, which is useful
  precisely when something is wrong. Restoring does: the files it replaces were
  written by the server as root, so a short-lived helper container does the work,
  the same way clearing stored data always has.
- A file that cannot be read is reported by name and count rather than silently
  left out of the archive.
