## What's new in 0.51.1 — releases now tell you when a file on your disk needs updating

Updating this manager pulls a new **image**. It cannot touch the two files that
live on your machine: your `.env` (it holds your password, so it is never
overwritten) and the `docker-compose.yaml` you downloaded once. When a release
changed one of those, the only thing that could tell you was the release notes —
and we kept forgetting to
([#167](https://github.com/tubalainen/reforger-server-manager/issues/167)).

Three things change that: the build now **fails** when a release edits those
files and its notes don't say so, `rsm update` checks your files on your own
machine, and the Windows start script reports settings your `.env` is missing.

## Do I need to do anything?

**Once, on Linux**, if you installed with `install-local.sh` or `install-vps.sh`:
your existing `rsm` command predates the new check and cannot refresh itself, so
fetch it once — after that it keeps itself current on every `rsm update`:

```bash
sudo curl -fsSL https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/scripts/linux/rsm.sh -o /usr/local/bin/rsm
sudo chmod 755 /usr/local/bin/rsm
```

**Windows and by-hand installs: nothing.** The Windows scripts already refresh
themselves on every launch.

## Updating your setup files

Nothing to add to your `.env` in this release, and the compose files are
unchanged. The `rsm` command itself changed — see above.

---

## `rsm update` now checks your files

After pulling, it compares your machine against the release and says what
differs:

- **`.env`** — lists any setting the release ships that your file does not have,
  with the example value. It never edits your `.env`; `rsm config` opens it.
- **`docker-compose.yaml`** — shows a diff against the release's version and
  offers to replace it, keeping your old one as `.bak-<timestamp>`. Say no and
  it prints the exact `curl` command for later.
- **`rsm` itself** — updates in place, and takes effect from the next run. (It
  is swapped by an atomic rename, so the copy the running shell is reading is
  never overwritten mid-run.)

`rsm check` runs the same checks without pulling anything.

## The Windows shortcut reports new settings

`start.ps1` already refreshed itself and its sibling scripts on every launch.
Now, in the same step, it compares your `.env` against the release's
`.env.example` and lists any setting you don't have. It only ever *reports* —
your `.env` is yours.

## The build refuses to forget

`scripts/ci/release_guard.py` runs in CI on every pull request. If `.env.example`,
a `docker-compose*.yaml` or the `rsm` script changed since the last release, the
notes for that release must carry an **"Updating your setup files"** section, and
must name every newly added `.env` key. Otherwise the check fails — and prints a
ready-made section listing exactly what changed.

It stays out of the way for ordinary releases: when a version only changes code
inside the image, pulling the image *is* the update, and no section is required.

`docs/release-notes/TEMPLATE.md` documents the house style and this rule.

## Small print

- The [v0.50.0 notes](https://github.com/tubalainen/reforger-server-manager/releases/tag/v0.50.0)
  have been corrected to carry the section they should have had — the three
  `AI_ORDER_*` settings it added to `.env.example` — both in the repository and on
  the Releases page. (The release workflow keeps a notes file and its release in
  sync only for the version currently in `backend/config.py`; correcting an older
  release is a one-off `gh release edit <tag> --notes-file …`, which is what was
  done here.)
- The README has a new
  [Updating your setup files](https://github.com/tubalainen/reforger-server-manager#updating-your-setup-files)
  section, per install type, and the in-app User Guide answers the same question
  in its FAQ.
