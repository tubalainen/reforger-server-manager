## What's new in 0.65.0: the Docker gate, and room for more than one install per machine

The manager no longer talks to Docker through a general-purpose socket proxy.
Each install now runs its own **Docker gate**. It is a small container with no
network at all, and it is the only part of the install that holds the Docker
socket. The manager reaches it over a socket file that only the two of them
share. The gate passes on only what the manager needs, for that install only.

- **Nothing can reach the Docker API over a network any more.** Not the game
  servers, their Workshop mods, or other users on the machine. This is the
  structural fix that v0.64.1 promised, and it works on any Docker version.
  The Docker Engine 28 requirement from v0.64.1 is gone.
- **What the manager may ask for is now checked, not just where it asks.** New
  containers may only use the two images named in `.env`, may never be
  privileged or share the host's processes, and may mount nothing but this
  install's own data and server-file folders. Exec, image builds, volumes and
  the rest of the Docker API are refused.
- **Several installs can share one machine** (#204). Each install is a *stack*
  with its own name, `RSM_STACK` in `.env`. Every container, network and volume
  it creates starts with that name. A manager sees and controls only its own
  stack: another team's servers do not exist as far as it can tell. A single
  install keeps the default name, `reforger`, which is every name it had
  before. Setting up a second stack is manual for now. See
  [Several installs on one machine](https://github.com/tubalainen/reforger-server-manager/blob/main/docs/installation.md#several-installs-on-one-machine).
  Tooling for several stacks comes in a later release.

## Do I need to do anything?

**Yes: the gate is wired in by the compose file, which only you can replace.**
See [Updating your setup files](#updating-your-setup-files). Until you do, the
new manager still works, and it keeps to its own containers on its own side.
But nothing below it enforces that, and the GUI shows a yellow **"This
manager's compose file is older than v0.65.0"** banner on every page.

When the new compose file is in place, the manager recreates each game server
the first time you start it. This gives the container its stack label, so the
gate lets the manager keep managing it. Saves, configs and mods are not
touched, since they live in the data folder and not in the container.

## Updating your setup files

**The compose files changed** (`docker-compose.yaml`, `docker-compose.vps.yaml`
and `docker-compose.windows.yaml`). The socket proxy service is replaced by the
gate, which runs the manager's own image. The Docker API network is gone.

**`.env` has one new setting, `RSM_STACK`.** It is optional: leave it out, or
set `RSM_STACK=reforger`, to keep every name as it is. Two settings are no longer
used. You can delete them, and nothing breaks if you leave them:
`DOCKER_PROXY_IMAGE` (there is no proxy image any more) and `DOCKER_NETWORK`
(the compose file now sets it from `RSM_STACK`).

If you pin `MANAGER_VERSION` in `.env`, set it to `v0.65.0` or later before you
take the new compose file. The gate lives in the manager's image, and an older
image does not have it.

### Installed with the Linux installer (you have the `rsm` command)

```bash
sudo rsm update
```

When it says your compose file differs from this release's, answer **y** to
replace it (a backup is kept). Then answer **y** again to recreate the stack.
Game servers stop briefly, and the ones set to auto-start come back.

From this release on, `rsm` fetches the setup files that match the version you
run. A pinned `MANAGER_VERSION=vX.Y.Z` gets that release's files, and `latest`
gets `main`'s. When it recreates the stack, `rsm` also removes the old
`reforger-docker-api` network, which is now unused. The `rsm` that runs this
update is still the previous one, so this happens from your *next* update on.
You can remove it by hand now with `docker network rm reforger-docker-api`.

### Installed by hand

From the folder with your compose file, download the new one. That is
`docker-compose.yaml`, or `docker-compose.vps.yaml` on a VPS. Then pull and
**recreate** the stack:

```bash
curl -fsSLO https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/docker-compose.yaml
docker compose pull
docker compose down
docker compose up -d --remove-orphans
docker network rm reforger-docker-api
```

(VPS: use `docker-compose.vps.yaml` in the download and add
`-f docker-compose.vps.yaml` to each `docker compose` command.) The last line
removes the old Docker API network, which nothing uses any more. It is safe
to skip.

If you build the image yourself (`build: .` instead of `image:`), do the same
for the new `docker-socket-proxy` service. The gate runs the manager's image.

### Windows

Re-run the installer. It keeps your `.env` and your data, and it replaces the
compose file:

```powershell
$installer = "$env:TEMP\reforger-install.ps1"
Invoke-WebRequest -UseBasicParsing https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/scripts/windows/install.ps1 -OutFile $installer
powershell -ExecutionPolicy Bypass -File $installer
```

Then start it from the Desktop shortcut as usual.

### Check that it worked

The yellow banner is gone after a reload of the GUI. `docker ps` lists a
`reforger-docker-gate` container, and there is no `reforger-docker-proxy` any
more.

## Small print

- The gate answers `GET /_rsm/gate` with its stack and version. That is how the
  manager tells a gate from an old proxy and warns in the GUI. A red banner
  appears if the manager and its gate disagree about the stack name.
- The manager's own container now carries labels for its stack and its port
  ranges. Tools that look at every stack on a machine can then keep the stacks
  apart without reading anyone's `.env`.
- Windows `stop.ps1 -All` and `uninstall.ps1` now touch only this install's
  containers, networks and volumes.
- The Linux installers no longer require Docker Engine 28.
- A new CI job starts two stacks on a real Docker host. It checks that each
  gate lets its own stack work and keeps it blind to the other.
- Known limit: the gate keeps a manager to its own slice of the machine. It is
  not a sandbox for a manager that has itself been taken over, because Docker
  follows symbolic links when it mounts a folder. The GUI login should still be
  treated as control of the machine. A follow-up
  ([#206](https://github.com/tubalainen/reforger-server-manager/issues/206))
  will close this by mounting through Docker volume subpaths.
