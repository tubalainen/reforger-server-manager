## What's new in 0.64.1: a security fix — the game servers could reach the Docker API

On Linux, a game server could reach the manager's Docker API. That includes any
Workshop mod running on it, since Reforger mod scripts can make web requests.
That API can create containers, which on a Docker host amounts to full control of
the machine. This release closes that path. **Every Linux install, local or VPS,
should apply it.** Windows is not affected.

## Do I need to do anything?

**Yes, on Linux — see [Updating your setup files](#updating-your-setup-files).**
Pulling the new image is not enough: the fix is in the compose file, which only
you can replace, and it takes effect only after the stack is recreated.

To tell whether a machine is still exposed, update the image first. The manager
checks its own setup and, until the fix is applied, shows a red **"Security: the
game servers can reach the Docker API"** banner on every page. It also writes
the same message to its log. The banner names the exact cause and clears by
itself once the fix is in place.

**Windows (Docker Desktop): nothing to do.** Docker Desktop keeps game servers on
a separate network inside its own VM, so they never had this path. The one
exception is a setup where you set `INSTANCE_NETWORK_MODE=host` in `.env` by
hand. Set it back to `auto`.

## Updating your setup files

The compose file changed (`docker-compose.yaml` and `docker-compose.vps.yaml`;
not the Windows one). No `.env` settings were added.

**First, Docker Engine 28 or newer is required.** Check with:

```bash
docker version --format '{{.Server.Version}}'
```

If it prints anything below 28, upgrade Docker first. Running the official
installer upgrades an existing Docker CE install:

```bash
curl -fsSL https://get.docker.com | sudo sh
```

### Installed with the Linux installer (you have the `rsm` command)

```bash
sudo rsm update
```

When it says your compose file differs from this release's, answer **y** to
replace it (a backup is kept). Then recreate the stack. Game servers stop
briefly, and the ones set to auto-start come back:

```bash
sudo rsm restart
```

From this release on, `rsm update` offers that restart itself whenever it
replaces the compose file. The `rsm` you run for *this* update is still the
previous one, so the restart has to be run by hand this once.

### Installed by hand

From the folder with your compose file, download the new one. That is
`docker-compose.yaml`, or `docker-compose.vps.yaml` on a VPS. Then pull and
**recreate** the stack. `down` before `up` is what makes Docker rebuild the
network with the new setting.

```bash
curl -fsSLO https://raw.githubusercontent.com/tubalainen/reforger-server-manager/main/docker-compose.yaml
docker compose pull
docker compose down
docker compose up -d
```

(VPS: use `docker-compose.vps.yaml` in the download and add
`-f docker-compose.vps.yaml` to each `docker compose` command.)

### Check that it worked

The red banner is gone after a reload of the GUI. To test it directly, this
should now print nothing and give up after 5 seconds:

```bash
docker run --rm --network host curlimages/curl -s -m 5 "http://$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' reforger-docker-proxy):2375/version"
```

## What was wrong

The manager has never held the Docker socket itself. Since v0.44.0 a small proxy
holds it, on its own `internal` network shared only with the manager. The intent
was that nothing else could reach it. `internal` turned out not to mean that:
Docker still gives such a network an address on the host, and the host can reach
every container on it.

That alone was harmless, until v0.45.2 moved the game servers to host
networking to fix player joins
([#150](https://github.com/tubalainen/reforger-server-manager/issues/150)).
From then on, network-wise the game servers *were* the host. So a game server
could reach the proxy, and so could any local user account on the machine. It
was found while planning
[#204](https://github.com/tubalainen/reforger-server-manager/issues/204) and
confirmed on a real install. We know of no case where it was used.

The fix is Docker's `isolated` gateway mode on that network. It gives the
network no address on the host, while the manager and the proxy still reach
each other. It needs Docker Engine 28.0 or newer. Engine 27 rejects the setting
and older engines silently ignore it, which is why both the installers and the
manager check the version.

## Small print

- The Linux installers now require Docker Engine 28 or newer and offer to
  upgrade an older one. `rsm check` and `rsm update` warn about an older engine.
- New endpoint `GET /api/system/warnings`, which the GUI shows as banners above
  every page. It is empty on a healthy install.
- A later release (#204) moves Docker access onto a local socket with no network
  at all. This fix stands on its own until then.
