## What's new in 0.43.7

### Fix: "readonly database" / "Permission denied" on a `/data` left over from an older version (#140)
After upgrading, saving a template or recovering an instance could fail with
`attempt to write a readonly database` and
`Permission denied: /data/instances/<id>/configs/server.json`, even though the
login and every read worked. The GUI looked alive but nothing could be saved.

The cause was file ownership. An older image ran as root and created the
database and the per-instance config folders under `/data` owned by root. The
current image runs as an unprivileged user and, on start, only re-owned the top
`/data` directory — not the files already inside it — so those root-owned files
stayed unwritable.

The container entrypoint now re-asserts ownership of the **whole** `/data` tree
on every start, so a `/data` created by an older (root) version becomes writable
again automatically. No manual `chown` needed.

If you prefer to fix it by hand instead of upgrading, from the host:

```bash
sudo chown -R 1000:1000 ./data      # Linux bind mount (docker-compose.yaml)
```

(Named-volume/Windows setups are fixed by the upgrade itself.)

**Upgrade:** the manager updates itself on start, or pull
`ghcr.io/tubalainen/reforger-server-manager:latest`.
